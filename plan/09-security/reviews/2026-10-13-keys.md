# Security review: how both OpenAI keys are handled (P8-01)

| Status | Owner | Updated | Feeds |
|--------|-------|---------|-------|
| reviewed | ai | 2026-10-13 | SR-02, SR-15, SR-19, #71 |

**Question (from the owner):** is the key a visitor saves for the session really stored securely,
and can anyone ever see the operator's key?

**Short answer.** Yes, now, within limits stated below:

- The operator's key never leaves the server. A canary test proves it for every API route, every
  page, the client bundle and the server log.
- A visitor's key goes only to this site, over HTTPS, in one header, and the server drops it with
  the request.
- In the browser it was kept as plain text. It is now sealed, and a remembered key expires after
  30 days.
- Two weaknesses in the rate limits that guard the key check were fixed.
- What no web page can protect against (a malicious browser extension, a compromised computer)
  is listed under "Residual risks", with the advice the panel now gives: use a project key with a
  monthly budget.

## Scope

The visitor's own key (P6-03, `x-openai-key`), the operator's key (`OPENAI_API_KEY`), and the
limits that stop this server being used to test stolen keys (`/api/key`). Read at `main` on
2026-10-13 (after #70), with the fixes on branch `fix/71-key-security`.

## Checks

| # | Area | Check | Evidence | Verdict |
|---|------|-------|----------|---------|
| 1 | Browser, at rest | What storage holds once a key is saved | Before: the raw `sk-…` string in `sessionStorage` or `localStorage`. Now: `v1.<tab\|device>.<expires>.<iv>.<ciphertext>`, AES-GCM under a non-extractable key in IndexedDB (`lib/visitor-key.ts`); e2e reads every storage and finds no `sk-` | **Fixed** |
| 2 | Browser, at rest | How long a remembered key lasts | Before: until Forget. Now: 30 days, with the expiry authenticated with the key, so it can't be extended by hand (`visitor-key.test.ts`, e2e) | **Fixed** |
| 3 | Browser, at rest | Keys stored as plain text by the earlier version | Sealed on first read, or dropped if they can't be (e2e) | **Fixed** |
| 4 | Browser | Which scripts can read the key | Only this origin's. CSP `script-src 'self' 'nonce-…' 'strict-dynamic'`, no `unsafe-inline`, no third-party scripts, no `innerHTML`, `frame-ancestors 'none'` (`server/csp.ts`, SR-15). YouTube runs in a `youtube-nocookie.com` iframe on its own origin | Holds |
| 5 | Browser | Where the key is sent | `keyHeaders()` is spread only into this site's own `fetch` calls. `connect-src 'self'`. Never a cookie (so no CSRF use), URL or body; secure contexts only (`canUseOwnKey`) | Holds |
| 6 | Browser | The input field | `type="password"`, `autocomplete="off"`, cleared once the key is kept, never shown again | Holds |
| 7 | Transport | Plain HTTP | The browser won't send it outside a secure context, and the server refuses it over plain HTTP except from this machine (`request-config.ts`); HSTS over HTTPS (`proxy.ts`) | Holds |
| 8 | Server | Validation | `VisitorKeySchema`: `sk-` + 20–300 of `[A-Za-z0-9_-]`, so nothing can be smuggled into a header or log line | Holds |
| 9 | Server | Lifetime | A fresh client per request, never the cached operator client (`knowledge.ts`); not in the spend ledger (`visitor-key.test.ts`) | Holds |
| 10 | Server | Logs and responses | `describeFailure` turns provider errors into fixed text; OpenAI's masked echo never passes. Visitor canary test (P6-03); operator canary test (new, below). The SDK redacts `authorization` in its own debug logs | Holds |
| 11 | Server | Caches | Key-dependent responses are `no-store` or `private`; nothing about the key is in them | Holds |
| 12 | Operator key | Reaching a browser | No `NEXT_PUBLIC_*`, no `next.config` `env`, and `@dear-steven/core/config` can't be imported by client components (`pnpm arch`). Now proven at runtime: `operator-key.test.ts` (every route on disk, with OpenAI echoing the key) and `e2e/operator-key.spec.ts` (a production server on a canary key: pages, RSC payloads, every script and stylesheet, every API route, DOM, storage, cookies, server log). Both were mutation-checked: a planted 8-character leak in `/api/status` fails them | **Proven (new tests)** |
| 13 | Key check oracle | The rate limiter | Before: once 10,000 clients were tracked, **every** bucket was cleared, including the global `keyCheckAll` and `accessAll`. Ten thousand requests with made-up addresses reset the limits on testing stolen keys and guessing the passcode. Now: only refilled entries are dropped, shared buckets are kept apart, and new clients wait while the map is full of limited ones (`rate-limit.test.ts`: a 20,000-client flood refills no one) | **Fixed** |
| 14 | Key check oracle | The client address | Before: the **first** `X-Forwarded-For` entry, which the client writes, so every request could claim a new address. Now: the entry the deployment's own proxy wrote (the last by default, `DEAR_STEVEN_TRUSTED_PROXIES`), or a platform header (`DEAR_STEVEN_CLIENT_IP_HEADER`); IPv6 by /64 (`client-address.test.ts`) | **Fixed** |
| 15 | Deployment | `OPENAI_BASE_URL` | The OpenAI SDK reads it from the environment: if the operator sets it, every call goes there, visitors' keys included. Operator-controlled; documented in `docs/DEPLOY.md` | Noted |

## Residual risks

- **A script running in the page** can use the sealing key and read the key. Sealing protects
  against reading the browser's files (a backup, an info-stealer scanning profiles for `sk-`). It
  cannot protect against code running as this site, and nothing in a browser can. The CSP is what
  keeps injected scripts out.
- **Browser extensions** with access to this site can read its storage and requests. A web page
  can't stop them.
- **A shared computer.** Tab storage is the default, and "remember" lasts 30 days at most.
  Forget removes the key and the key that sealed it.
- **Several tabs.** Forget in one tab removes the sealing key, so keys kept in other tabs stop
  opening and are dropped. This fails safe.
- **Rate limits are per process** (ADR-001). Several instances would need a shared store.
- **A determined attacker with many real addresses** gets many buckets. The daily cap (SR-02)
  bounds the operator's bill; the key check never spends.

## Advice now shown to visitors

"Safest: a project key with a monthly budget." A project key with a spend limit caps the damage
of any leak, wherever it happens, and can be revoked on its own.

## Not in scope

Keeping keys on a server, or accounts (P8-05, for a decision).
